# Qualify retained PDF reports, native exports, and restore

Status: implemented; qualification runs in the CLI integration suite.

Source baseline: `2d100a274a548a9eb1e7f9aaef12eab478c78a1f`, after PR #754.
Parent scope: [report/export workflow, #719](https://github.com/kenn-io/docbank/issues/719).

## Outcome and boundary

An operator with retained PDF originals and available text evidence should be
able to capture a selected-document report, review its dates, save the report
and exact originals, and recover the workflow from a physical backup. Recovery
must distinguish a saved request from a live report and must reject a selection
whose current documents have changed.

This slice takes the workflow qualification and restore outcomes from closed
PRs [#518](https://github.com/kenn-io/docbank/pull/518) and
[#530](https://github.com/kenn-io/docbank/pull/530). It does not adopt their code
or reopen their cumulative feature stacks. The current contracts come from the
implemented [selected-report](2026-09-29-exact-document-reports-design.md),
[native-export CLI](2026-09-29-cli-native-exports-design.md),
[MCP export](2026-09-30-mcp-native-exports-design.md),
[MCP report](2026-10-01-mcp-search-reports-design.md), and
[CLI recovery](2026-10-01-cli-report-recovery-design.md) designs.

**The starting point is retained evidence.** The daemon currently registers
plaintext, EPUB, and Docling ASR rendition runtimes. PDF adapters exist as
library components; this slice does not install or register a PDF runtime.
Tests will publish synthetic PDF evidence before starting the daemon and then
exercise the existing operator commands. This qualifies consumption and
durability of retained evidence, not fresh PDF extraction, OCR accuracy, or
agreement between an extractor and a PDF's visual contents.

The expected implementation is focused integration tests and any necessary
correction to the owning usage guide. No new command, endpoint, packet format,
schema migration, dependency, processing runtime, retention policy, or general
test framework is proposed. A discovered defect must first be reproduced; a
change to a product contract needs a separate design decision.

Execution exposed a defect in content-date extraction: retained Markdown escapes
date punctuation, so the report missed labeled ISO dates and used vault-addition
fallbacks. The scanner now recognizes escaped date punctuation in rendition
evidence, including numeric dates that require interpretation. Raw tokens, quotes,
byte offsets, and evidence hashes still refer to the retained bytes. Native-text
matching is unchanged. A focused regression and the full PDF workflow reproduce
and cover this correction; no report contract changes.

## Why this slice

Current tests establish useful pieces separately:

- `internal/mcp/report_workflow_test.go` connects selection, date review,
  frozen report bytes, and native export using text documents.
- `cmd/docbank/report_inspect_test.go` shows that history survives a daemon
  restart while live report handles do not.
- `internal/store/term_report_history_test.go` round-trips reusable requests
  through metadata export/import.
- `internal/processing/package_supplied_text_backup_test.go` restores a
  searchable supplied-text artifact through physical backup. Its PDF-named
  source is a placeholder payload, not a structurally valid PDF.
- `cmd/docbank/cli_test.go` exercises physical backup and restore commands,
  including the restored storage proof.

None of those tests follows one retained PDF selection through report review,
original export, physical backup, and a newly started restored daemon. That is
the gap this design addresses. Adding catalog reads or redaction first would
leave that gap; redoing the entire workflow independently in the CLI, MCP, and
browser would multiply fixtures without resolving a different restore contract.

## Corpus and evidence setup

Use four small, structurally valid, one-page PDFs generated from synthetic
text. The existing `github.com/go-pdf/fpdf` dependency and examples in
`internal/pdfstamp/synthetic_test.go` provide the generation pattern. Check
that each generated original opens as one page with
`github.com/pdfcpu/pdfcpu` v0.15.0 (`api.PageCount`).
Compute its expected size and SHA-256 directly from the generated bytes before
writing it to the vault. Use distinct bytes for every original and replacement.

| Document | PDF body and retained evidence | Selected |
| --- | --- | --- |
| `alpha.pdf` | `Alpha. Document dated 2024-05-06.`; matching retained text | Yes |
| `beta.pdf` | `Beta. Document dated 2024-05-06. Document dated 2024-06-07.`; matching retained text | Yes |
| `missing.pdf` | `Alpha beta.`; no retained text | Yes |
| `excluded.pdf` | `Alpha beta. Document dated 2024-05-06.`; matching retained text | No |

These are unrelated documents with singleton families. No attachment or family
expansion is involved. The excluded document would change both terms' counts
if the selected scope leaked. The missing document would change both counts
if reporting silently read or processed its original instead of disclosing
unavailable text.

Publish normalized page evidence, sanitized Markdown, rendition authority,
and lexical projections through `processing.ArtifactPublisher.PublishRendition`.
Follow `publishRenditionTextFixture` in
`internal/api/routes_rendition_text_test.go`; it is an existing package-local
test pattern, not an importable fixture API. Every `PublishRendition` call
needs a fresh `LexicalGenerationID` as well as distinct build and attachment
IDs. Reusing the fixture's constant generation ID retrieves an earlier stored
index; the publication coverage check then rejects the later build. A fixture
probe confirmed that failure before daemon startup. Do not substitute
`RecordExtraction`, SQL inserts, mocked report responses, or files that merely
have a `.pdf` extension.

The fixture owns the store and blobs only during setup, then closes both before
starting the real daemon. All subsequent report, export, mutation, and backup
operations use the daemon-backed CLI or its existing HTTP client. Restore uses
the existing backup command into an empty, isolated target. No test opens the
store underneath a running daemon.

Configure one explicit portable profile whose fingerprint matches the retained
renditions; give it no executable PDF provider binding. Derive the `archive`
processing profile and its referenced rendition/retrieval blocks once from one
configuration value. Reuse those exact blocks for fixture publication, source
daemon startup, and each restored daemon. Assert the loaded configuration
resolves to the published fingerprint at every start. Report profile selection
uses that configured profile independently of runtime registration. Evidence
setup must not run again after restore. Successful restored reports must use
the retained authority and bytes, with the missing document still disclosed as
missing. This tests operation without a PDF runtime; it is not a general proof
about network activity or unrelated background processing.

## Report and export contract

The request uses `selected_documents` containing the captured node ID, current
version ID, and original SHA-256 for the three selected PDFs. It names the
configured profile, uses UTC and `available_only`, and has two simple terms:
`alpha` and `beta`. Both ranges are `2000-01-01` through `2099-12-31` inclusive.
Assert that the fixture's vault-addition fallback date lies inside that range.
The wide range deliberately includes the missing document's fallback date;
packet membership alone does not guarantee inclusion in coverage.

Creation returns a `needs_review` report. Retrieve its date candidates, identify
`beta.pdf` by document identity, and select its `2024-05-06` document-date
candidate using the returned candidate ID and evidence hash. Do not hardcode
those derived identities. Revision produces a complete child with the parent's
expiry. The parent remains review-pending and cannot be downloaded.

The completed report must satisfy these literal expectations:

| Observable result | Expected value |
| --- | --- |
| Packet members | Exactly the three selected identities |
| Each term's five count columns | `1, 1, 1, 1, 1`, in the existing column order |
| Aggregate and each term's coverage | 3 scoped, 2 searchable, 1 missing text, 0 incomplete families, 1 fallback date |
| Missing evidence | Explicitly disclosed; no contribution to either term's hits |
| Excluded document | Absent from packet membership and both terms' counts |

Use `search-export show --json`, verified download, offline `verify`, and `csv`
to observe these results. Parse packet members and CSV rows independently of
the calculator; do not derive expected values by calling the production count
function. Offline verification establishes internal packet consistency, not
that retained text accurately describes an original PDF. Preserve its
`source verified: false` distinction.

Also submit a strict request selecting only `missing.pdf`, with the same
in-range fallback. It must return `incomplete_coverage` and publish no packet.
Keeping this separate avoids ambiguity about whether pending date review or
missing coverage is reported first.

Export the same three original versions through `export preview`, `start`,
`status`, `download`, and `release`, using fresh caller-supplied operation IDs.
Request only originals. Verify the archive with the existing bundle verifier,
then compare its member identities, original bytes, sizes, and hashes against
the fixture's independently captured values. No excluded document or rendition
attachment may appear. A nonempty ZIP or a successful verifier alone is not a
sufficient assertion. Release the completed job; retry only `export_retained`
within a bounded test deadline if the finished download's lease still exists.

Native export accepts retained historical versions. Report creation requires
the selected versions to remain current. Tests must preserve this distinction.
For the historical export after replacement, omit the optional node-revision
precondition (revision zero); retain the exact old version, hash, and size.
Do not include the trashed document in that historical-export request.

## Frozen reports and two backup states

Take a verified physical backup after the reviewed report and original export,
while all three selected versions are current. Call this the **current-selection
snapshot**. Save the reviewed report packet and native archive outside the vault
and restore targets.

Then replace `alpha.pdf` with a different valid PDF and trash `missing.pdf`
through the daemon. Re-reading the already captured child summary and downloading
its packet must return the original frozen result, including identical packet
bytes. A new report from the old selected request must fail with
`report_selection_changed`; it must not silently skip the trashed document or
substitute the replacement. Take and verify a second physical backup, the
**changed-selection snapshot**. Its history must still contain the earlier
reviewed run and reusable request.

Restore each snapshot into its own empty target and start a new daemon using
that target. The source daemon must be stopped before switching CLI homes;
connections, goroutines, and files must close before each target is removed.
Check the backup restore's content, SQLite integrity, and manifest-statistics
proof, then check the following user-visible behavior:

| After restore | Current-selection snapshot | Changed-selection snapshot |
| --- | --- | --- |
| `history --json` | Original request and receipt remain | Original request and receipt remain |
| `show` / `download` with the old report ID | `report_unavailable`; no newly published file | Same |
| New report from the saved request | Fresh report, needs date review again | `report_selection_changed` |
| After a new review | Same expected members, counts, and coverage | No substitution or automatic recreation |
| Fresh native export | Same three original versions and exact bytes | Export the replaced document's still-retained historical version and verify its old bytes |

History deliberately clears date choices. Recovery extracts only the saved
request, obtains fresh candidates, and reviews the ambiguous PDF again. It does
not copy the old receipt's counts into a new result. The fresh report ID and
observation are new; do not require byte-identical regenerated ZIPs or identical
timestamps. Byte identity applies to repeated downloads of one live frozen
report and to original PDF content.

Backup excludes `config.toml`. Before starting a restored daemon, explicitly
provision the same synthetic portable processing profile, preserving the
restore's own storage configuration and using fresh local paths. Do not copy
credentials, runtime records, provider endpoints, or the source backup binding.
Restoring metadata must not be presented as restoring deployment configuration.

Previously saved report packets and original archives must still verify
offline after the source daemon stops. A saved packet remains useful even when
its old live handle is unavailable. This design does not promise recovery of
live caches, export jobs, download tickets, or reviewed date choices from history.

## Test scope and completion evidence

The new complete scenario belongs with the existing real-daemon CLI integration
tests. Split it at useful fixture boundaries if needed; keep one small corpus
and explicit assertions. Reuse the existing CLI, daemon-start, PDF-generation,
and backup patterns. Add only local test helpers required by these scenarios;
there is no product fixture command or shared workflow framework.

Run existing MCP report/export workflow tests as regression coverage. Do not
repeat the physical restore matrix over MCP HTTP, stdio, and the browser. Their
current tests remain evidence for their own boundaries; this slice makes no
new claim of PDF-specific browser or MCP transport qualification.

Use isolated temporary homes, backup repositories, and output directories with
synthetic data only. Poll actual readiness and export job state with deadlines;
do not sleep until expiry or replace the real worker with canned responses.
Keep each daemon below the existing eight report handles per API-key owner,
including revisions. Release finished native exports so their two shared
owner slots are reusable. A new report-release feature is outside this scope.

The new tests must execute in the normal `fts5` suite with both CGO/mattn and
pure-Go/modernc SQLite. Keep Linux, macOS, and Windows paths portable; native
platform execution is required before claiming those platforms qualified.
Compile-only checks or a local Linux pass cannot establish that claim.

Implementation evidence must name the exact revision, commands, SQLite modes,
and platforms actually exercised. Keep actionable work and status in kata;
this document defines the acceptance contract. Update the existing search-export
or backup guide only where the scenario reveals an operator-facing omission.
Public documentation must describe implemented behavior, not proposed tests.

This closes the retained-PDF CLI report/export and restore evidence gap once
the scenarios pass. It does not close all of #719. Fresh PDF preparation,
attachment/family workflows, PDF-specific browser acceptance, and broader
maintenance qualification remain distinct acceptance questions. Catalog reads
from #533, plan inspection from #583, and PDF redaction remain separate work.
